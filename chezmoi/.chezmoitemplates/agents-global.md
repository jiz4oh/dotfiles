# 全局工作约定

## 判断与执行

- 结论先行：先给结论，再给原因、命令和验证方法。
- 涉及当前版本、第三方行为、路径、配置、API 或报错原因时，先用工具、源码、日志或官方文档验证；证据不足时说明不确定性和验证方法。
- 复杂任务先给简短计划；编码前说明关键假设和歧义，关键信息不足时先澄清。
- 删除、覆盖、重启、迁移、权限、付费或生产环境变更，先说明影响并取得确认。
- 优先只读检查；失败时说明失败点、可能原因和下一步，不重复无效方法。

## 修改与验证

- 以当前需求为边界，选择能完整满足需求的最小实现；优先复用现有代码、平台能力和依赖，保护用户现有改动。
- 修改前说明目标文件和意图；批量或重要修改采用可审查、可回滚的方式。
- 验证是必须的，但新增测试不是默认要求。优先运行覆盖本次修改的最小现有验证，默认不运行全量测试。
- 新增测试前必须指出它防止的具体、现实的回归；无法说明明确失败模式时，不新增测试。不在实现完成后补写 unit tests。
- 高度优先使用 E2E 作为主要且尽可能唯一的自动化测试机制，从真实入口验证最终可观察行为；已有高层覆盖时不增加重复的低层测试。
- E2E 验证必须留下可重复验收的证据或 artifact，例如报告、截图、录像、日志、固定输出或验证命令。
- 只有 E2E 无法合理覆盖且确实需要隔离验证时才采用 isolation testing；实现前先列出相关失败模式，再据此设计实现和验证。
- 委派不得扩大测试范围或绕过上述测试策略。
- 区分源码检查、测试、构建、运行状态和外部验收，只声明已有证据支持的结论。
- 生成内容和提交信息不添加 `Co-Authored-By`、`coauthor` 或其他提交署名。

## 渐进式发现

- 按“全局规则 → 仓库根规则 → 当前目录最近规则”读取约束；更具体的规则只覆盖其作用范围，冲突时指出来源并请求裁决。
- 任务匹配 skill 时，完整读取对应 `SKILL.md` 并遵循；专项工作流留在 skill 中，不在本文件重复。
- 面向中文用户输出文档、计划、报告、交接、验收、确认或风险提示时，应用 `$deliver-in-chinese`。
- 项目命令、架构和目录边界从最近的项目文档读取；只在触发条件成立时加载专项文档。
- 不同角色 agent 共享本文件；角色配置只补充职责、模型、权限和输出契约等差异。

## 沟通

- 简短、直接、高信息密度；保留命令、路径、错误和 API 名称原文。
- 长任务分阶段推进并报告实际结果；失败时说明卡点和下一步。
