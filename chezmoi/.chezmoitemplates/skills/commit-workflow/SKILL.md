## 提交边界与顺序

- 修改 Git 历史前，先检查分支、`HEAD`、上游分支、merge/rebase 状态、暂存区和完整工作区。
- 每个提交只承载一个可验证、可独立审查的意图；相互依赖且无法独立成立的生产代码改动放在同一个提交中。
- 拆分提交时以行为和依赖边界为准，不为了制造更多提交而机械拆分文件或代码块。
- 遵循本流程时，测试单独放入 `test:` 提交。该提交只包含测试，并排在其所验证的生产代码提交之后。
- 当改动涉及多种生产代码提交类型时，在依赖顺序允许的前提下按 `fix` → `refactor` → `feat` 收敛；依赖关系优先于类型顺序。
- 不把无关修改、顺手重构、格式化或其他工作区改动带入当前提交序列。

## 提交信息

- 使用一行 Conventional Commit 标题，格式为 `<type>: <祈使式摘要>`，例如 `feat: expose line-item allocations` 或 `test: cover refund allocations`。
- 使用最能表达该提交主要意图的类型；不要为了满足提交顺序而错误分类。
- 不写 scope、body 或 trailer。
- 不添加 `Co-Authored-By`、`coauthor` 或其他提交署名信息。

## 提交时间间隔

- 多提交序列中的时间戳必须按时间先后排列，不能晚于本地当前时间；相邻提交至少间隔 300 秒。
- 分钟和秒应采用不同取值，且分钟字段与秒字段都不能是 `00`。
- 不要为了等待提交时间间隔而延迟提交。按正常提交流程立即创建提交；提交成功后，再调整该提交的 author 和 committer 时间，使多提交序列满足上述时间顺序和间隔要求。
- 调整提交时间或以其他方式重写提交前，先确认目标提交尚未发布、暂存区和工作区干净，且没有正在进行的 merge 或 rebase。
- 重写前创建恢复用 ref；除非用户要求修改内容，否则验证最终提交树未变。
- 调整后核对 author 和 committer 时间戳、相邻提交间隔，以及最终提交树。

## 暂存与验证

- 只暂存明确审查过的路径或代码块；保留无关的已暂存、未暂存及未跟踪改动。
- 每次提交前检查暂存路径列表、完整暂存 diff 和空白错误，确认 staged 内容与该提交的单一意图一致。
- 遵循当前生效的全局和项目测试策略，运行范围最小且适用的验证；提交本身不构成新增测试的理由。
- 如有测试或验证未运行，应如实说明，不得暗示其已通过。
- 每次提交后核对提交目的、文件范围和实际 diff；整个序列完成后核对提交顺序、时间戳和工作区状态。
- 除非用户明确要求 push，否则提交只保留在本地。
